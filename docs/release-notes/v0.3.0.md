# CanIToolCall v0.3.0

This release is about answering **"will my model's tool calls parse on engine X?"** without a checkout: a `lookup` command, a versioned `matrix.json` with per-model results, an MCP server and status badges. The probe can now test the OpenAI Responses API and run as a GitHub Action. Coverage grows by two model families (MiniMax M2.x and ByteDance Seed-OSS), one engine adapter (mlx-lm), and a vLLM pin moved from 0.30.0 to 0.34.0.

**The committed results snapshot is unchanged.** `results/2026-11-15/` was taken at the 0.2.0 pins (vLLM 0.30.0) over 500 fixtures, and the README table still shows it. The new families, the mlx-lm adapter and the vLLM 0.34.0 pin are replayed by the nightly matrix, not by a committed snapshot. Where these notes give numbers for them, those are local replays reported in their PRs, and each one says which version it was run at.

## Ask the matrix without a checkout

- **`canitoolcall lookup NAME [--engine E] [--json]`** (PR #50). Give it a family (`qwen3-hermes`) or a model (`Qwen/Qwen3.5-9B`). It reads the published `matrix.json`, or the file or URL given with `--matrix`. For a model name it reports that model's own results where the matrix has them, and otherwise says the row covers the whole family. The exit code is 0 whenever the lookup works, even if the status is `fail`, so scripts should read `status` from `--json`.
- **`matrix.json` has a versioned schema** (`schema_version` "1.0", `spec/matrix.schema.json`, also published at its `$id`). It adds optional `family_info` and per-model results in each cell. Existing fields are unchanged. The live file was built before this change and has no `schema_version`. `lookup` rejects it with an explanation until the site is next rebuilt from `main`, which the nightly does. Until then, use `--matrix` with a newer file.
- **`canitoolcall mcp`** (PR #52, issue #29): a stdio MCP server, installed with the optional extra `canitoolcall[mcp]`. Its tools are `lookup`, `list_families`, `list_engines` and `probe`. The operator decides where `probe` may send requests. By default that is loopback only, with no API key. `--allow-base-url` adds targets, and `--allow-api-key-env VAR=URL` binds a key to one exact URL. A tool caller cannot change the matrix source, and cannot reach a target or use a key that the operator did not allow. The MCP `probe` still sends `/chat/completions` only.
- **Badges** (PR #51). The site writes shields.io endpoint badges per cell and per engine, from the same data as `matrix.json`. Cell pages show a Markdown snippet to copy.
- **Site** (PR #48): page descriptions, preview tags, `--site-url` canonical links and a `sitemap.xml`.

## Probe

- **`probe --api {chat,responses,both}`** (PR #56) sends the same nine scenarios to `/v1/responses`, non-streaming and streaming, with the same judgments plus Responses stream consistency. The default stays `chat`, so existing runs and exit codes are unchanged. Report outcomes gain an `api` field. It is tested against the test suite's mock server only. No real engine's `/v1/responses` has been probed yet, so please run `--api both` against yours and report what you see.
- **A GitHub Action** (PR #57). `uses: redd34/canitoolcall@v0` runs `probe` in CI, writes a results table to the job summary, uploads the JSON report and fails the job on the probe's exit code. It works from 0.3.0 on: the moving `v0` tag points at the latest 0.x release, and the `version` input defaults to `0.3.0`. The key is passed by variable name only. Pin a full commit SHA if you want supply-chain safety. The Ollama example in [`docs/github-action.md`](https://github.com/redd34/canitoolcall/blob/main/docs/github-action.md) is marked untested. The self-test workflow runs the action against the mock server.

## Coverage

- **MiniMax M2.x** (`minimax`, PR #53, part of #4). 23 fixtures: 18 renders through the pinned MiniMax-M2.1 template and 5 token-prefix truncations. M2, M2.5 and M2.7 were checked to render identically. vLLM (`minimax_m2`) and SGLang (`minimax-m2`) have parser mappings. llama.cpp, Ollama and transformers report the family `unsupported`, which here means "not replayed there", not "the engine has no support". **No MiniMax replay results exist yet.** The PR had no engine environment, so the nightly is the first run. MiniMax-M3 is not included.
- **ByteDance Seed-OSS** (`seed-oss`, PR #60). 30 fixtures: 20 template renders at rev `497f1dc`, 6 truncations and 4 cases from llama.cpp's `test-chat.cpp`. vLLM (`seed_oss`) and the llama.cpp autoparser have mappings. SGLang, Ollama and transformers have no Seed-OSS parser at their pins. Local replays on macOS arm64 gave:
  - vLLM: `pass=19 soft_pass=3 fail=8`. These are **recorded at vLLM 0.30.0 and not re-run at 0.34.0.** The Seed-OSS parser files are byte-identical, but the `Qwen3Parser` they inherit from changed.
  - llama.cpp `a25c9865`: `pass=23 soft_pass=1 fail=6`.

  None of these failures is triaged or reported upstream. Two fixtures expect JSON values that the template writes as Python `str()` literals. They follow the template and ByteDance's original parser, not a recorded generation.
- **mlx-lm 0.32.2 adapter** (PR #58). It runs `mlx_lm.server`'s own chat-completions handler with the tool parser that mlx-lm picks for each repo. gpt-oss, DeepSeek and Llama come out `unsupported`. A full local replay on macOS arm64 covered the 500 fixtures from before MiniMax and Seed-OSS: `pass=187 soft_pass=73 fail=35 unsupported=205`. The 35 fails are not triaged. The Linux path (`mlx-cpu` wheels) has not been run. If mlx does not import there, setup exits 3 and the nightly skips the column. mlx-lm is not in any committed snapshot.
- **vLLM pin 0.30.0 → 0.34.0** (PR #59). No parser name the adapter uses changed. `llama3_json` and `llama4_json` now resolve to `LlamaJsonEngineToolParser` (vllm#63569), and the adapter follows 0.34's serving path. A local replay of the 500 fixtures on macOS arm64, compared with the snapshot's vLLM 0.30.0 results:
  - pass went from 270 to 291, soft pass from 93 to 94, and fail from 135 to 113;
  - 21 cases went from fail to pass and 1 from fail to soft pass, with no regressions;
  - most of the change is in `llama`, where pass went from 9 to 26.

  Four vLLM findings no longer reproduce in that replay. The committed triage and the README table still describe 0.30.0 until the next snapshot.

## Fixtures and spec

- **555 fixtures** (500 in 0.2.0) in 11 families: 23 MiniMax, 30 Seed-OSS, and 2 Mistral v3 cuts that stop before the list's closing `]` (PR #47). Every call in those cuts is complete, so a correct parser keeps them all (recovery contract section 2).
- **Fixture spec unchanged at 0.2.** The only new schema is `matrix.json`'s, at its own version 1.0.
- The notes of three 0.2.0 derived cuts that keep every call no longer say "the unfinished call must not be returned" (PR #47).

## Tools and triage

- Both upstream-PR verifiers validate replay reports with one shared module, `scripts/replay_report.py` (PR #54). They print the `unsupported` count on the `fixtures replayed` line and in their JSON reports (PR #49).
- Triage (#23, PR #55): the last `transformers-other` case is now the finding `transformers-gemma4-content-overwritten` (`engine_bug`). That brings the snapshot's triage to 35 engine-bug findings, and no transformers case is left untriaged. 27 cases remain `untriaged_discrepancy`: SGLang 14, llama.cpp 7, Ollama 6.

## Upgrading

```sh
uvx canitoolcall@0.3.0 --version
pip install 'canitoolcall[mcp]'   # only for canitoolcall mcp
```

Fixture files written for 0.2 still validate, because the spec did not change. `lookup` reads `matrix.json` files with `schema_version` 1.x. A file built by canitoolcall older than 0.3 is rejected with an explanation.
